# Admin Dashboard Architecture

Frontend-only admin dashboard for the UAE auto parts eCommerce site, built inside the existing
Next.js App Router project (`frontend/`). The real PHP backend does not exist yet for these
endpoints — the admin runs end-to-end against an in-browser mock API (MSW) that mimics the final
REST contract byte-for-byte, so swapping to the real backend later is a one-file (really: one env
var) change.

## 2. How the mock API layer works

- `NEXT_PUBLIC_ADMIN_API_URL` (default `/api/admin`, see `.env.local.example`) is the base URL
  `lib/admin/api-client.ts` builds every request against.
- `NEXT_PUBLIC_ADMIN_USE_MOCKS` (default `true`) controls whether `MSWProvider` boots the MSW
  browser worker. When it's `"false"`, `MSWProvider` renders children immediately and never
  imports `mocks/admin/browser.ts` — so the mock code isn't even bundled into that path in
  production if you additionally strip the `mocks/` folder at build time.
- `mocks/admin/db.ts` holds plain in-memory arrays (products, categories, vehicles, orders,
  customers, pages, seoMeta, settings, mediaItems, adminUsers) seeded with 30–50 realistic
  records each: UAE emirates, AED prices, bilingual English/Arabic names for
  categories/brands/products/pages. Seeding uses a deterministic seeded RNG (`mulberry32`) so the
  data is stable across dev-server restarts, not re-randomized every reload.
- `mocks/admin/handlers.ts` implements every endpoint in §3 using MSW v2's `http`/`HttpResponse`
  API, mutating the `db.ts` arrays directly (create/update/delete persist for the lifetime of the
  page — a full browser reload resets to the seed data).
- Every handler returns the same envelope the real backend uses:
  `{ success, data, error, message }` (see `frontend/src/types/api.ts`).
- **Login accepts any syntactically valid email + 6-character password** — a deliberate mock
  convenience so you can demo the flow without memorizing seeded credentials. It logs you in as a
  matching seeded admin (`admin@autopartsuae.ae` / `manager@autopartsuae.ae`) if the email
  matches one, otherwise as the default admin. The real backend will obviously do real credential
  verification — this is mock-only behavior, not a pattern to carry over.

### Swapping to the real API

1. Set `NEXT_PUBLIC_ADMIN_API_URL` to the real PHP backend, e.g. `http://localhost:8000/api/admin`.
2. Set `NEXT_PUBLIC_ADMIN_USE_MOCKS=false`.
3. Done — `api-client.ts` never branches on mock-vs-real, so no code changes are needed. The PHP
   backend must implement the same `{success,data,error,message}` envelope and endpoint list
   below for the frontend to keep working unmodified.

## 3. Endpoints (all under `/api/admin`)

| GET | `/auth/me` | Current admin user (also re-validates the token) |

| GET | `/dashboard/stats` | Revenue/orders/customers/products counters |
| GET | `/dashboard/analytics` | Sales-by-month, orders-by-status, top products |
| GET/POST | `/products` | List (search/category_id/status/pagination) + create |
| GET/PUT/DELETE | `/products/:id` | |
| POST | `/products/bulk` | `{action: "delete"\|"activate"\|"deactivate", ids}` |
| GET/POST | `/categories`, GET/PUT/DELETE `/categories/:id` | |
| GET | `/vehicles/years`, `/vehicles/makes`, `/vehicles/models` | Cascading Year→Make→Model filters |
| GET | `/vehicles` | Paginated full list |
| POST | `/vehicles/import` | Bulk import, skips existing (year,make,model) rows |
| GET | `/orders` | List (search/status/pagination) |

| GET/PATCH | `/customers/:id` | |

| GET/PUT | `/seo` | List / upsert one entry by `id` or `path` |

| GET | `/reports/sales` | Sales-by-month + orders-by-status + totals |

## 4. Coding conventions

**React Query keys** — factory in `lib/admin/query-keys.ts`, always `["admin", resource, ...]`:
```ts
adminQueryKeys.products.list({ search, page })   // ["admin","products","list",{search,page}]
adminQueryKeys.products.detail(id)                // ["admin","products","detail",id]
```
Never hand-write a query key array inline — add it to the factory so invalidation stays
consistent (`queryClient.invalidateQueries({ queryKey: adminQueryKeys.orders.list() })` matches
every filtered variant).

**Forms** — `react-hook-form` + `zod` via `@hookform/resolvers/zod`, mirroring the existing
storefront `LoginSchema` pattern:
```ts
const Schema = z.object({ email: z.string().email(), password: z.string().min(6) });
const { register, handleSubmit, formState: { errors } } = useForm({ resolver: zodResolver(Schema) });
```

**Tables** — `components/admin/ui/DataTable.tsx` wraps `@tanstack/react-table`. Pages define a
`ColumnDef<T>[]` and pass `{ columns, data, isLoading }`; don't build ad-hoc `<table>` markup in a
page file.

**Toasts** — `react-hot-toast` (`toast.success(...)` / `toast.error(...)`), same as the
storefront's `AppProviders`. Mutations report success server-side messages via
`toast.success(response.message)` where the mock returns one.

**Mutations** — plain `@tanstack/react-query` `useMutation`, invalidate the relevant
`adminQueryKeys.*.list()`/`.detail()` on success. Don't roll custom fetch-and-setState logic in a
page component — always go through `lib/admin/api-client.ts`.

**Styling** — reuse the existing Tailwind design tokens (`bg-card`, `text-foreground`,
`bg-primary`, `border-border`, etc. from `tailwind.config.ts` / `globals.css`) — the admin has no
separate palette. `components/ui/Button.tsx` and `components/ui/Input.tsx` (the storefront's, not
admin-specific) are reused as-is since they're already token-driven and locale-agnostic.

**Auth** — `lib/admin/auth.ts` stores the JWT pair in `localStorage`
(`admin_access_token`/`admin_refresh_token`), completely separate from the storefront's
HttpOnly-cookie auth (`lib/api/client.ts`) — the two auth systems never share storage keys or
tokens. `useAdminAuthStore` (Zustand, persisted under `admin-auth-storage`) holds the current
admin user for the sidebar/topbar; `RequireAdminAuth` is the single guard component every
`(protected)` page passes through via the shared layout.

## 5. Known gaps (deliberately out of scope for this phase)

- No create/edit forms yet for products/categories/pages/vehicles — list views only, wired to
  real (mock) GET endpoints. POST/PUT/DELETE handlers exist and are ready to be wired up.
- No Tiptap rich-text editor wired into the Pages editor yet (dependency is installed).
- No pagination *controls* in the UI (the mock API supports `page`/`per_page` and returns `meta`,
  but list pages currently just request page 1 with a larger `per_page`).
- Forgot-password is a pure UI simulation (no backend endpoint was in scope for Phase 0).
- 2FA enrollment (`two_factor_enabled` exists on the user shape) has no UI yet.
